# Profilo — instructions for agents

Personal business-card pages (Polish-language competitor of about.me). Standards: `docs/standards/` (set 1.4.0, see `docs/standards/COPY.md`) — follow this copy. Product: `docs/product/`. Design: `docs/design/`. Architecture: `docs/architecture.md`. API contract: `docs/api/openapi.yaml`.

## Technical profile

- Backend: Python 3.15, FastAPI, Pydantic 2, SQLAlchemy 2 (async, asyncpg), Alembic migrations
- Code style backend: Ruff (lint + format), mypy strict
- Database: PostgreSQL 18; time as `timestamptz` UTC; public ids UUID v7
- Cache / rate limiting / broker: Valkey 9
- Background jobs: Celery 5 + Celery Beat (single instance)
- API: REST JSON, `/api/v1`, camelCase fields, Problem Details (RFC 9457) with `code`, page pagination (`page`, `perPage`, default 20, max 100), contract-first OpenAPI 3.1 checked in CI
- Auth: JWT access token 15 min (PyJWT, HS256) in memory; rotating refresh token in HttpOnly `SameSite=Strict` cookie, 30 days; Argon2id via pwdlib
- Bot protection: ALTCHA (self-hosted proof-of-work) on registration after threshold
- Files: user images on a persistent volume via fsspec; Pillow processing, EXIF stripped, WebP variants; served via `/media/**` through the API
- E-mail: SMTP adapter in `notifications` (Jinja2 templates; Celery task retries only transient errors — 4xx, connection — with exponential backoff and full jitter, at most ~8 min; 5xx/authentication fail at once; `email_failed` logged at error level with the SMTP code only, never provider text with addresses); Brevo on servers via `.env.secrets` written by the deploy workflow; Mailpit locally
- Frontend: Next.js 16 App Router, React 19, TypeScript strict, Node.js 26 LTS; one app for landing, `/user/{nick}` (SSR, no data cache) and panel
- Styling: `docs/design/tokens.css` and `docs/design/components.css` imported globally (design-system class names), CSS Modules for page layout; icons Lucide
- Forms and API client: React Hook Form + Zod; `openapi-typescript` + `openapi-fetch` generated from the contract; `@dnd-kit/sortable` for link order
- Code style frontend: ESLint + Prettier
- Tests: pytest + httpx (backend), Vitest + Testing Library (frontend), Playwright (E2E main flow and smoke tests); coverage threshold 95 % per app (quality-checks standard)
- Contract check: `api/scripts/check_contract.py` compares the FastAPI spec with `docs/api/openapi.yaml` (implemented paths, methods, 2xx statuses, request/response property names recursively; an object with fields on one side only is a difference)
- Dependency audits: `pip-audit` (runtime deps, hashes) and `npm audit --omit=dev` fail on any advisory; dev-only npm advisories fail at high/critical, moderate/low are reported only
- Images: base images pinned to patch version + digest; Dependabot weekly for uv, npm, Docker, Compose, GitHub Actions
- UI language: Polish only; product docs and code in English
- Runtime: Docker Compose (caddy, client, api, worker, beat, db, valkey); same Compose for staging and production
- Hosting: production planned on Hetzner Cloud CX33 with off-site backups to a Storage Box (ADR 0004); staging on the owner's shared VPS behind its nginx (docs/runbook.md „Shared host”)
- Backups: `backup` service in the server Compose (image `profilo-backup` from `infra/backup/`, published by CI like api/client): restic over SFTP, daily database + media at 02:30 UTC, 30-day retention, monthly restore test into a temporary database, alert e-mails; production only (settings and keys from `PROD_BACKUP_*` via the deploy workflows; docs/runbook.md *Backups*)
- CI/CD: GitHub Actions `ci.yml` (job `check` runs `make check audit secrets` and the prod builds, with a GHA layer cache; `publish` pushes `ghcr.io/michalwrzesinski/profilo-{api,client}:<sha>` on main); actions pinned to commit SHAs; images in GHCR; staging auto-deploy on main; production by `deploy-production` workflow started manually by the user (no GitHub environments — see overrides)
- Servers: Ubuntu 24.04 prepared by `infra/server/bootstrap.sh` (Docker, ufw 22/80/443, unattended upgrades, `deploy` user with SSH key only), or a shared host by `setup-shared-host.sh`; stack `infra/server/compose.yml` + `Caddyfile` in `/srv/profilo`; `deploy.sh <sha>` pulls, dumps the database, migrates, starts the release in the idle colour (`api-blue`/`client-blue` or `-green`), points Caddy at it after `/ready`, smoke-tests and points Caddy back on failure; `--rollback` only to a commit in `.deployed-history` (docs/runbook.md)
- Staging deploy: `.github/workflows/deploy-staging.yml` after CI succeeds on main (or manually with a SHA); secrets `STAGING_*`; on success it sets the commit status `deploy/staging`, which `deploy-production.yml` requires. Production: `deploy-production.yml` / `rollback-production.yml`, secrets `PROD_*`. All three run `infra/ci/deploy-remote.sh` from main with the deployed commit's stack files (docs/runbook.md)
- Monitoring: Sentry (EU region) in api, worker, the Next.js server and the browser (through the API's tunnel `/api/v1/monitoring/sentry`); release = commit SHA, created with source maps by the deploy workflows' *Sentry release* job; Better Stack Uptime on `/ready` and a heartbeat of the daily backup (docs/runbook.md *Monitoring*)

## Project overrides of standards

- No admin panel in v1 (product brief); operator actions via CLI commands in the `api` image.
- Mode without an agent account (project-setup standard): the agent works on the user's GitHub account `MichalWrzesinski`. Rules forbidding changes to repository settings, branch protection and environments still apply, although not enforced technically. Production deployment (`deploy-production` workflow) is started only by the user (rollback: see below); the agent reports readiness and gives the workflow link (overrides deployment standard: the agent never starts the production workflow).
- Free GitHub plan (user decision 2026-11-09, when the repository was private; it is public now, MIT licence since 2026-11-16): no branch protection, no GitHub environments (so no environment secrets and no deployment approval), no GitHub secret scanning. Compensation:
  - The agent never pushes to `main` and merges only through a PR with a green `check` and an approving review by the reviewer subagent.
  - Secrets are repository-level. Only `deploy-staging`, `deploy-production` and `rollback-production` reference deployment secrets; the agent never adds secret references to other workflows. Production secret names are prefixed `PROD_`.
  - `deploy-production` and `rollback-production` run only on `workflow_dispatch` from `main` and stop unless `github.actor` and `github.triggering_actor` (re-runs) are `'MichalWrzesinski'`. This guard only blocks other accounts: the agent acts as the same account, so keeping the agent away from production is a behavioural rule, not a technical control.
  - Starting `deploy-production` is the user's approval; the agent never starts it. `rollback-production` follows the deployment standard: the agent may start it without consent (only images deployed to production before) and informs the user immediately.
  - Secrets needed at runtime (Sentry, Brevo, Storage Box, uptime keys) reach the servers only through the deploy workflows; release creation and source-map upload to Sentry also happen there, never in `ci.yml`.
  - Secrets: gitleaks as a local pre-commit hook and in the `check` job (both added in iteration 0). A secret is caught before commit locally, but after push if the hook is bypassed — accepted gap.
- Pre-commit hook is a plain script in `.githooks/pre-commit` (installed by `make hooks`), not the `pre-commit` framework named in TASK-001: the framework needs Python on the host, which conflicts with the devops standard (only Docker and make). It runs gitleaks, then Ruff and Prettier on the staged content using the dev images from `make up`.
- `scripts/setup-github.sh` changes repository settings, so only the user runs it (e.g. again after upgrading to GitHub Pro, which would restore branch protection and environments).

## Conventions

- Commit area tags by path (first matching row wins). Task tag: `[TASK-NNN]` from `docs/tasks/`.

  | Path | Tag |
  |---|---|
  | `api/**` (incl. `api/Dockerfile`, migrations, tests) and `docs/api/openapi.yaml` | `[api]` |
  | `client/**` (incl. `client/Dockerfile`, unit tests), `docs/design/tokens.css` and `docs/design/components.css` | `[client]` |
  | `e2e/**` (Playwright) | `[client]` |
  | `infra/**`, `.github/**`, `.claude/**`, `docker-compose*.yml`, `Makefile`, `.env.example`, `.pre-commit-config.yaml`, `scripts/**`, other root config files | `[infra]` |
  | `docs/**` (other than above), `README.md`, `AGENTS.md`, `CLAUDE.md` | `[docs]` |

  A contract change in `docs/api/openapi.yaml` goes into the `[api]` commit that implements it, before the `[client]` commit that uses it.
- No AI attribution in commits or PRs (git-workflow standard).

## Commands

- `make up` (first run creates `.env`), `make down`, `make logs`, `make migrate`, `make check` (= lint + test + contract), `make audit`, `make secrets`, `make images`, `make ci` (all of the CI job), `make e2e` (Playwright main flow against the running stack, also the CI job `e2e`), `make format`, `make api-shell`, `make hooks`.
- Only Docker and make are needed; tools run in containers (`docker compose run --rm api|client …`). Host Node/Python versions are irrelevant.
- Backend tests use the `profilo_test` database (`TEST_DATABASE_URL`), created by `infra/postgres/init/`.
- Checks run as the host user (`--user $(id -u):$(id -g)`) so they work on Linux runners; the client image keeps `node_modules/.vite-temp` world-writable for that.

## Pitfalls

- Celery workers do not reload code: after changing tasks run `docker compose restart worker beat`; after `docker compose build api` recreate the containers (`docker compose up -d api worker beat`), otherwise they keep the old image. The Next.js dev server can keep stale module state after switching branches: `docker compose restart client`.

- `client/src/lib/api/client.ts`: only the exact token endpoints (`/auth/login`, `/auth/refresh`, `/auth/logout`, `/accounts`) are sent without the access token; any other endpoint, also under `/auth/`, gets it.
- A named volume takes its ownership from the image the first time it is created: after changing a directory's owner in a Dockerfile (e.g. `/data/media`), rebuild the image and recreate the volume (`docker volume rm profilo_media`), otherwise the app user cannot write. API tests use `MEDIA_URL=memory://media`. Draft images need the access token, so the editor shows them with `OwnerImage` (blob URL), never a plain `<img src>`.
- The E2E browser reaches the app as `http://caddy`: the Next.js dev server allows that origin (`allowedDevOrigins`), otherwise pages never hydrate. `make e2e` deletes the local `rl:*` rate-limit keys first, because every run registers a new account.
- E2E test accounts use `TEST_PASSWORD` from `e2e/tests/helpers.ts`, marked `// gitleaks:allow` (a local throwaway password, not a secret); keep that the only place.
- The editor preview is an iframe of `/podglad` fed by `postMessage` (same origin only) and the landing frames `/przyklad`; the page CSP (`client/src/lib/csp.ts`, set by `src/proxy.ts`) sends `frame-ancestors 'self'` for those two paths and `'none'` everywhere else — add a path to `FRAMABLE_PATHS` before framing another page. A client component using `useSearchParams` needs a `<Suspense>` around it in its page, or the production build fails.
- The client reads `PUBLIC_BASE_URL` at request time (robots.txt, sitemap.xml), so those routes and every page that needs it are `force-dynamic`; a static page would bake in the build-time value. Private pages get `noindex` from a server `layout.tsx` that re-exports the client `Shell.tsx` (client components cannot export metadata). Do not block them in robots.txt: crawlers would never see the `noindex`. X (Twitter) fetches the Open Graph card only because robots.txt allows `/api/v1/public/profiles/*/og-image.jpg` (the JSON endpoint next to it stays closed). The API (`public_base_url`) and the client must get the same `PUBLIC_BASE_URL`; on servers both read it from `/srv/profilo/.env`. Raise `og_image.VERSION` when the card design changes, otherwise cached cards stay for 7 days.
- Files the API serves only with the access token (draft images, the QR code) are fetched with `authorizedFetch` and shown or downloaded from blob URLs; build absolute URLs (`window.location.origin`) because the Vitest `mockFetch` cannot resolve relative ones. The editor top bar must fit 320 px: on phones Panel and Udostępnij are icons and „Opublikuj zmiany” is shortened.
- New e-mail templates (or any Celery task change) need `docker compose restart worker beat` before trying them locally: the old worker fails with `KeyError` on the template name and Mailpit stays empty. E2E finds mails by subject (`linkFromMail` in `e2e/tests/helpers.ts`).
- Lock order is always account first: login and refresh take the account `FOR SHARE`, password reset/change and deletion `FOR UPDATE`, and one-time e-mail tokens are locked after their account (`accounts/one_time.lock_with_account`). Keep that order, or a concurrent refresh survives the revocation (READ COMMITTED does not see rows committed during the `UPDATE`). Access-token checks compare `iat` with `password_changed_at`, which is set by the database clock at registration: API and database must share the clock (same host).
- After adding a route directory under `client/src/app/` the Next.js dev server may answer 404 for it (and for other new routes) until `docker compose restart client`; E2E then times out waiting for the form.
- API tests truncate `accounts` only: rows in other tables a test creates (e.g. `reserved_nicks`) must be cleaned up; `clean_state` removes quarantines. Celery tasks are sync and call `asyncio.run`: in async tests run them with `asyncio.to_thread(task.run, ...)`.
- Scheduled jobs go through `app.core.jobs.run(name, coroutine)`: it takes the Valkey lock and disposes the database engine and the Valkey client afterwards, because every Celery run has its own event loop (`asyncio.run`) and both are bound to a loop. Test the coroutine directly (async test) and the task wrapper with `jobs.run` monkeypatched. Media tests share one `memory://` storage for the whole run: assert on your own keys, not on totals. Try a job locally with `docker compose exec worker celery -A app.worker call <task name>` (after `docker compose restart worker beat`).
- The E2E browser reaches the app at `http://caddy`, which is not a secure context: `crypto.subtle` (and other secure-context APIs such as the async Clipboard API) do not exist there. Browser code that needs them must have a fallback (see `lib/proofOfWork.ts`). E2E registrations from one IP are limited (10 per hour, a challenge from the 4th attempt); the whole suite uses 9: create owners with `registerAccount`/`owner` from `e2e/tests/helpers.ts`, which solve the challenge, and keep new specs within the budget. `make e2e` clears the `rl:*` keys first; a second run of single specs within the hour may need `docker compose exec -T valkey valkey-cli --scan --pattern 'rl:register*' | xargs -r docker compose exec -T valkey valkey-cli del`. API tests turn the challenge off (`no_registration_challenge` in `conftest.py`) except in `test_proof_of_work.py`.
- A module that creates a web worker (`new Worker(new URL('./x.worker.ts', import.meta.url))`) must not be imported by that worker, not even indirectly: the production build (Turbopack) then loops forever at „Creating an optimized production build” while the dev server and E2E work. Keep the worker's code in a separate module (`proofOfWorkSolver.ts`). Run `make images` (or `docker build --target prod -f client/Dockerfile .`) locally after adding a worker; CI's `check` job stops after 30 minutes.
- Staging runs on a shared VPS behind the host's nginx (`TLS_MODE=proxied`, `compose.proxied.yml`, `setup-shared-host.sh`, `nginx-profilo.conf`; runbook „Shared host”); `bootstrap.sh` is for a dedicated server only. Caddy placeholders cannot nest (`{$A:{$B}}` breaks parsing): give defaults in `compose.yml`. Test server-side changes with the real `deploy.sh` in a `docker:cli` container (`--network host`, the Docker socket, `COMPOSE_PROJECT_NAME` set so it does not replace the local `profilo` stack).
- Entry points that do not start through `app.main` (the operator CLI, the Celery worker) must `import app.models`, or the ORM cannot resolve foreign keys to tables of modules that were not imported and fails on flush. API tests import the whole app, so test such entry points in a subprocess (`tests/test_blocking.py`).
- Responses that must not reveal whether an account exists (password reset request) do the lookup in a FastAPI background task with its own session (`get_sessionmaker()`), after the 202 is sent; never add work that depends on the account before the response.
- After changing `docs/api/openapi.yaml`, regenerate client types with `docker compose run --rm client npm run api:types`; `make lint` fails when they are out of date.
- Nick rules live twice — `api/app/modules/profiles/nicks.py` and `client/src/lib/nick.ts`; change both; their test cases live in `docs/api/nick-cases.json` (mounted into both containers). Forms that send credentials use `method="post"` so a submit before hydration never puts them in the URL.
- API tests use Valkey database 1 and truncate tables per test (`clean_state` fixture); never point them at a shared database.

- ESLint stays on 9 (marked unsupported upstream) because `eslint-config-next` 16 depends on `eslint-plugin-import`, `eslint-plugin-react` and `eslint-plugin-jsx-a11y`, which all cap ESLint at 9; Dependabot ignores ESLint majors. Migration: TASK-025.
- `vitest` and `@vitest/*` must be updated together (Dependabot group `vitest`).

- The Next.js dev server does not pick up changes to `docs/design/tokens.css` or `components.css` (outside `client/`): `docker compose restart client` and reload the page.
- The client image is built with the repository root as context (`client/Dockerfile`, root `.dockerignore`) because the app imports `docs/design/tokens.css`. Fonts come from `next/font` (self-hosted); do not add the Google Fonts `@import` to the app.
- Local ports bind to `127.0.0.1` only (8080 app, 8025 Mailpit).
- The API trusts `X-Forwarded-*` only from `FORWARDED_ALLOW_IPS` (uvicorn default `127.0.0.1`); staging/production must set it to the Caddy container network, otherwise client IPs (rate limits) are wrong.
- The API has no access log by design (no visitor IPs in app logs); request ids link Caddy and API logs.
- On the servers the app services are `api-blue`/`api-green` and `client-blue`/`client-green`; the serving colour is in `$APP_DIR/caddy/live` (written after Caddy loaded `upstreams.caddy`). Operator commands target the live colour (runbook `live` helper); a new server-side service that takes requests needs both colours and an entry in `deploy.sh`'s `app_services`.
- `deploy.sh` skips migrations only when the database's revision (`alembic_version`) is unknown to the release (database ahead: rollback); any other error stops the deployment. A rollback relies on backward-compatible migrations — a migration that breaks the previous release also breaks its rollback.
- Caddy reads `$APP_DIR/caddy/Caddyfile` (copied by `deploy.sh`), not the release directory: changing Caddy's own settings in `compose.yml` (image, ports, variables, mounts) recreates it with a ~2 s gap; Caddyfile changes are reloaded without one.
- Never `docker compose up` the live colour's `api-*`/`client-*` on a server: it recreates the serving container in place and drops requests. Changes go through a deployment (a new colour).
- The deploy workflows' jobs that reach the server get a read-only `GITHUB_TOKEN` (it is handed to the server for the registry login); writing (release tag, commit status) happens in separate jobs that never touch the server. Keep it that way.
- `infra/backup/profilo-backup`: never pipe `pg_dump` into `restic backup --stdin` (a failed dump still leaves a truncated snapshot as "latest"); use `--stdin-from-command`. Jobs run as a separate process (`"$0" __job`) because `set -e` is ignored inside a function called in `… || status=$?`. Scheduler marks are written after a job finishes: deployments recreate the container mid-job.
- The restic encryption key (`PROD_BACKUP_PASSWORD`) must also be kept outside GitHub by the user; GitHub secrets cannot be read back, and without the key the backups are useless.
- Error reports must not carry personal data: a new request field with a secret uses the `Password` type (or calls `core.monitoring.redact`) so its exact value is scrubbed; never put e-mails or tokens in log fields or exception messages on purpose, and never log expected conditions at error level — every error-level log entry becomes a Sentry event.
- The browser SDK has a placeholder DSN and only the tunnel: do not give the client a real DSN or allow Sentry hosts in CSP. The tunnel accepts error events only; sessions, tracing and replays stay off (`instrumentation-client.ts`).
- Sentry's JS SDK 11 has no `sendDefaultPii`: collection is controlled by `dataCollection` (defaults collect user data, cookies and headers — keep them switched off). The Python SDK uses `data_collection`.
- Dependabot waits 14 days after a release (`cooldown`, the two-week rule); a PR with a younger version is closed, not merged. The Playwright image (`docker-compose.yml`, `mcr.microsoft.com/playwright:vX-noble`) and `@playwright/test` in `e2e/package.json` must have the same version (the image's browsers match one library version): bump both in one PR. New Python minors are planned changes (ignored by Dependabot).
- Page CSP (TASK-024): scripts only with the per-request nonce (`'strict-dynamic'`, no `'unsafe-inline'`), set by `client/src/proxy.ts`; Caddy adds a strict policy only where a response has none. Consequences: every page renders per request (`await connection()` in the root layout — no static pages); a hand-written inline `<script>` or a third-party script must get the nonce (`(await headers()).get('content-security-policy')`), or it is blocked; a new web worker or external origin needs its own directive in `csp.ts`; never put a nonce into `style-src` (browsers would then ignore `'unsafe-inline'`, which the inline styles still need). E2E specs record CSP violations (`recordViolations` in `e2e/tests/helpers.ts`) and fail on any; the local Caddy has the servers' fallback policy.
- A CSS grid column of `1fr` is at least as wide as its widest content (`minmax(auto, 1fr)`): on phones use `minmax(0, 1fr)`, or one long control pushes the page past 320 px. The main E2E flow checks the private pages at 320 px (`expectNoSidewaysScroll` names the elements that stick out).
- Staging VPS (shared host): the provider blocks outgoing ports 25, 465 and 587 (host and containers; the server's own firewall accepts all output), so staging sends through Brevo on port 2525 (runbook „Shared host” step 9). Never point staging SMTP at port 465/587, nor at a mail server on the VPS (it could not deliver: port 25). SMTP settings live only in GitHub (`STAGING_SMTP_*`): the deploy workflow overwrites `.env.secrets` on every deployment.
- Compose named volumes `client_node_modules` and `client_next` shadow the bind mount; after changing `package.json` run `docker compose build client` and `docker compose up -d --renew-anon-volumes client` (or `make down` + remove the volume).
